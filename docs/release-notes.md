## 本次更新（1.9.2）—— 修复拖动悬浮窗时的随机闪退

> 1.9.1 为了消掉拖动撕裂，把拖动交给了 Windows 的系统移动循环。撕裂确实没了，
> 但那条路会**随机闪退**：按住悬浮窗标题栏一拖，先卡住，然后程序直接消失，
> 日志里连一行"程序退出"都没有。这一版换掉了搬窗口的方式，配置与数据无需迁移。

### 症状

- 按住悬浮窗标题栏拖动（移动超过 4px），偶发卡顿后进程直接消失
- 系统事件日志里是 `RocoMerchantAssistant.exe ... 出错模块 ucrtbase.dll ...
  异常代码 0xc0000409`；程序自己的日志停在最后一次查询成功，没有异常栈

### 根因

`SendMessage(WM_NCLBUTTONDOWN, HTCAPTION)` 依赖系统模态移动循环，而这个循环会把
鼠标消息**同步**派发回窗口过程；Tk 的窗口过程会就地重入 Python 绑定，此刻该线程
正因为 ctypes 的 `Py_BEGIN_ALLOW_THREADS` 而处于"没有 Python 线程状态"的状态，
CPython 直接 `Py_FatalError`（`PyEval_RestoreThread: ... the GIL is released`）
→ `abort()`。所以它没有 traceback，是"硬崩溃"。

### 修复

- 删掉系统移动循环（`window_move.begin_drag`），搬窗口改回 Tk 自己的 `wm geometry`
- 新增**帧合并**：`<B1-Motion>` 只记录最新目标，每帧最多搬一次窗口
  （本帧第一个事件立即搬，保证跟手；其余合并到帧末）。一帧只有一个位置，
  既不撕裂，也不会再重入 Python
- 松手时先落地最后一段位移，位置不丢；窗口销毁时停掉帧节拍
- **新增 `logs\crash.log`**：用 `faulthandler` 兜住 C 层硬崩溃，把崩溃瞬间所有线程的
  Python 栈写进文件。这类崩溃不经过任何 Python 异常钩子——1.9.1 那次 `app.log` 里
  一个字都没留，只能靠系统事件日志反推；以后同类问题有现场可查了

实测（真实悬浮窗 + 合成高密度鼠标拖动）：81 个移动事件 → 34 次搬窗，
跟手误差 1–2px；修复前同一脚本 5 次里崩 3 次，修复后连跑 6 次全通过。

## 本次更新（1.9.1）—— 拖动撕裂与高刷适配修复

> 1.9.0 把界面推倒重写，视觉上了一个台阶，但**拖动窗口会"撕"**，动画节拍也写死在
> 60fps 附近，在 120Hz / 200Hz 这类屏幕上尤其明显。这一版只修这些，不引入新功能，
> 配置与数据文件无需迁移。

### 修复：拖动悬浮窗时画面撕裂

**现象**：按住悬浮窗标题栏拖动，窗口边缘出现一条"错位"的撕裂带，鼠标动得越快越明显。

**根因**：拖动是每个 `<B1-Motion>` 事件调一次 `wm geometry` 自己搬窗口。鼠标回报率高时
每秒数百个事件，而 Tk 的每一层控件都是独立窗口，搬一次要把几十个子窗口重排重绘一遍
（本机实测 **9.6ms/次**），远超一帧的预算（200Hz 下只有 5ms）。于是同一帧里父窗口已经
到了新位置、子控件还停在原地，合成出来就是半成品画面。

**修复**：按下并超过系统拖动阈值（4px）后，把这个手势交给 Windows 的**系统移动循环**
（`ReleaseCapture` + `WM_NCLBUTTONDOWN/HTCAPTION`）。系统原子地搬整个窗口，应用一次
绘制都不参与，因此与刷新率彻底解耦；松手后仍会做多屏边界校正与位置落盘。

- 阈值内的微小抖动不算拖动，标题栏的**双击打开主窗口**照旧可用
- 拖动结束后才写 `floating_geometry`，中途不会被数据刷新"拽回去"
- 万一某些系统不认无边框窗口的 `HTCAPTION`，会自动回落为应用内拖动并记一条日志

### 适配高帧率显示（上限 90fps）

- 读真实刷新率（`EnumDisplaySettingsW`）换算帧间隔，**封顶 90fps**：再高肉眼收益极低，
  而每一帧都要重排重绘，无脑吃满 200Hz 只是白烧 CPU
- 动画期间按引用计数把系统定时器精度提到 1ms（Windows 默认 15.6ms 粒度会把
  "每帧 11ms"变成"每帧 15.6ms"），动画结束立刻归还
- 所有动画从"每帧走固定比例"改成**给时长 + 按真实经过时间推进**：悬停 90ms、
  描边 120ms、滚轮 3 视口/秒。**帧率变了速度不再变**
- 滚轮滚动、卡片入场、按钮悬停共用同一套帧节拍，不再出现 65fps / 42fps 这种写死的节奏

### 消除动画闪烁

- 按钮、状态胶囊、滚动条拇指改为**复用 Canvas item**（只改颜色/坐标），
  不再每帧 `delete("all")` 重画——那是"先擦成底色再画"，高刷屏上每帧都看得见闪
- 状态胶囊宽度固定：「营业中」→「换货校验中」时，右上角倒计时不再左右跳

### 修复：快速滑动仍然撕裂

**现象**：慢速滚动已经顺了，但快速拖动滚动条 / 猛转滚轮时仍会看到错位与拖影。

**根因**：一帧里要重绘的内容太多。Tk 每个控件都是独立子窗口，实测每张卡片约
**13 个子窗口、约 0.5ms/帧**——视口内 12 张就吃掉 90fps 的 11ms 预算（每帧位移
130px 以上时实测 11–15ms）；而拖滚动条时每个鼠标事件都直接 `yview_moveto`，
1000Hz 鼠标下同一帧里能搬十几次，一次拖动可能瞬间要求 300–500px 的位移。

**修复**：

- 拖滚动条改为"事件只更新目标，搬动交给帧节拍"：**每帧最多搬一次**，按"视口/秒"
  推进（12 视口/秒 ≈ 每帧 90px），不再一帧跳到底
- 新增**帧时长闭环**：用实测帧间隔反推速度，帧被拖长就自动降速（最低 35%），
  回到预算内再逐步提速。宁可少滚一点，也不再present 半成品帧
- 滚轮速度仍是 3 视口/秒（每帧约 23px，实测 5ms，稳在预算内）

**试过但放弃的方案**：把视口外的卡片 `grid_remove`（"只画看得见的"）。实测切换
可视行时要重算整张 grid 并触发 `<Configure>` 级联，**115ms/帧**，比不做（32ms）
还慢得多。Tk 里真要虚拟化只能整卡 Canvas 化或位图滚动，属于另一个量级的改动，
见开发手册第 11 章。

### 修复：展开历史时"空白卡片 → 文字 → 图标"分步出现

**现象**：点「展开历史」，先看到一排排空白卡片边框，随后文字一块块出现，图标再一块块补上。

**根因**（三条叠加）：

1. 展开是"先显示容器、再往里建卡片"——`_body.pack()` 在 `_rebuild()` 之前，
   容器先上屏，内容是后填的。
2. 本机 Tk 的布局/映射成本约 **1.4ms/控件**（连空 Frame 都一样），20 张商品卡片
   ≈ 260 个控件，光"算位置 + 首绘"就要 ~400ms。这段时间 Windows 会把画好的
   那一部分逐帧推上屏——所以看到的是"分步填字"。
3. 图标各自触发一次磁盘解码，且 `ImageLoader` 在"这个图标正在下载"时**直接丢弃**
   后来的回调，于是一部分卡片会一直停在占位字母上，直到下次刷新。

**修复**（逐轮构建 + 每轮完整上屏）：

- 不再"先挂容器再往里塞卡片"：改成**逐轮构建**——第一轮同步建好就上屏，
  其余轮次按"一帧一轮"续建。点击返回约 90ms 就能看到内容，而不是盯着静止画面
- 每一轮内部**冻结重绘**（`WM_SETREDRAW` + `RedrawWindow`）：这一轮的卡片、
  文字、图标同时出现，不会出现"空白卡片先出来、再填字、再补图标"
- 建卡片前先 `prewarm()` 把所有图标解码进内存：磁盘命中的图标与文字同帧就位
- `ImageLoader` 在加载进行中改为**排队回调**而不是丢弃，图标不会再有"不出来"

实测（本机 2560×1440@200Hz）：4 轮 ×5 件，首轮内容 ~90–140ms 出现，455ms 全部到齐；
8 轮 ×5 件 728ms 全部到齐，每 ~110ms 补一轮，图标 100% 与卡片同帧。

**代价与边界**：轮与轮之间有一次约一帧的空档（用来看清上一轮），所以"全部到齐"的总时长
比"整块憋着一次显示"略长（4 轮 455ms vs 313ms）。换来的是点击立刻有内容、且全程没有空白。
再往下只有两条路：把每张卡片的 13 个控件砍到 7 个左右（每轮 90ms → ~50ms），
或改成单画布渲染（一屏一个窗口）。都是另一个量级的改动，见开发手册第 11 章。

**顺带说明**：`WM_SETREDRAW` 与坑表里那个 `WS_EX_COMPOSITED` 死锁不是一回事——后者是
扩展样式让 DWM 合成与 Tk 几何计算互等；前者只丢弃绘制消息，实测冻结期间 `update()`
依旧 0.2ms 返回。

### 其它修复

- **日志查看器里 WARNING 行不再高亮**：1.9 的主题重构把日志级别字面量 `" WARNING "`
  误替换成了 `" theme.WARNING "`，永远匹配不到
- 卡片入场动画的延时任务现在可撤销：以前在入场动画（约 240ms）内再刷新一次，
  回调会落到已销毁的卡片上，异常被 Tk 吞掉，表现成"界面出错"或界面停住不动
- 悬停/描边动画在控件销毁时自动停表（切主题重建控件树、关对话框时不再残留回调）
- 展开历史后拖窗口边缘，不再让每张历史卡片逐事件重排（列数变化才重排）
- 设置/网络面板的"已复制"提示、主窗口的临时置顶，回调都加了存活保护

### 验证

- 自测 **340 → 386 项**全过（新增帧节拍夹取、动画可取消、Canvas item 复用、
  日志警告着色、拖动契约不可变、冻结重绘可嵌套、加载中回调不丢、逐轮构建等用例）
- 自测不再受"当前是否营业"影响：`frozen_clock()` 把时钟钉在营业时段，凌晨跑也一致
- 真机（2560×1440@200Hz）：拖动悬浮窗、拖窗口边缘改大小、滚轮、切主题、双击标题栏

## 本次更新（1.9.0）—— 全面重构与界面大改

> 这是本程序发布以来最大的一次更新：代码架构按功能分层重构，界面支持
> Windows 11 风格与多主题，滚动、内存、通知体验全面优化。功能行为与
> 1.8.0 完全兼容，配置与数据文件无需迁移。

### 架构重构（对使用者透明，对贡献者重要）

- 全部运行时模块收进 `roco/` 包，按五层组织：`core/`（纯领域逻辑，零界面依赖）、
  `net/`（数据渠道与解析）、`services/`（缓存/调度）、`platform/`（托盘/通知/自启等
  Windows 能力）、`ui/`（界面，唯一允许碰 Tk 的地方）。依赖方向严格单向。
- 823 行的渠道模块拆成「渠道与降级」（providers）、「页面解析」（parsing）、
  「轮次模型」（rounds）三块，改页面结构不再牵动轮次逻辑。
- 主窗口拆出视图控制器（app_controller）：取数编排、换货校验、历史落盘、
  通知决策全部独立于界面——界面层现在只负责"画"。

### 新增：多主题外观

- **四种主题模式**：深色（默认）/ 浅色 / 纯黑（OLED，省电且与息屏融合）/ 跟随系统
- 「跟随系统」通过注册表变更通知**推送式**感知 Windows 明暗切换（无轮询、即时生效）
- **自定义强调色**：6 个预设色块，或填任意 #rrggbb
- Windows 11 质感：圆角窗口（自带系统阴影）、标题栏明暗随主题、Mica 云母
  （22H2+，老系统自动跳过）；设置、日志等弹窗不再有白屏闪烁

### 体验优化

- **滚动流畅度**：滚轮改为匀速缓动动画（约 60fps 连续平滑），滚动条重绘去重
- **加载过渡**：查询结果卡片瀑布式入场，图标渲染前预热同步就位，消除"逐条弹出"的闪烁
- **内存占用**：后台常驻自动修剪工作集（实测工作集 62MB → 5–7MB，私有提交 33MB），
  图标内存缓存封顶 256 张
- 悬停反馈带渐变过渡，界面顶部新增主题色饰线

### 开发者

- 新增开发脚本：`scripts/dev.bat`（自动挑带 tkinter 的解释器启动）、`test.bat`、
  `check.bat`（提交前门禁）、`logs.bat`（直达日志目录）
- 340 项自测全绿；架构约定与视图协议见开发手册

## 本次更新（1.8.0）—— 历史货架、按物品提醒、已购标记、跨日修复

### 新增：历史售卖物品

换货后就再也拿不到上一轮了——数据源只给"当前这一轮"。现在每次查询都会按
「日期 + 轮次」记一份，保留最近 7 天（最多 28 轮）。

- **默认折叠**，标题上写明有几轮；展开后按时间倒序：最新的 **20:00 在最前**，
  然后 16:00 / 12:00 / 08:00
- **保留全天在售商品**：条件球、棱镜球这类四轮都卖的东西本来就是那一轮货架的一部分，
  历史里不做剔除
- 同一轮重复查询（重试、手动刷新）只更新内容，不会堆出一堆重复记录
- 打烊、空货架不会被记成一条"什么都没卖"的假历史
- **没有历史时不能展开**：展开按钮为禁用态（「暂无历史」），标题行也不响应点击
- 设置 →「历史记录」可以关闭该功能（不写盘、不显示），或把存放目录改到别处；
  改目录时已有记录自动迁移，目录不可写会回退默认位置并提示

### 新增：按物品选择通知

以前只能按品质粗筛（史诗 / 传说以上），想单独盯"国王球"会把同品质的球一起通知；
而"可可果球"这类限时活动道具品质不高，永远进不了阈值。现在两者并行：

- 设置 →「通知提醒」→「关注物品」→「选择…」，勾选要提醒的物品
- **关注物品不看品质**，上架就提醒；原来的品质阈值继续生效，两条规则取并集
- 清单可更新，来源有三处：
  1. Wiki 抓取（`商店一览` 的常驻条目 + 正文提到远行商人的条目，含图标）
  2. **本机实际见过的商品自动累积**——只要上过一次架，就能被选到
  3. 手动添加（新活动道具名字已知、还没上架时用）
- 图标优先用缩略图：同一物品同时有 100px 小图和 Wiki 原图时选小的，省流量也省磁盘

> 为什么不是"从 Wiki 抓一份完整清单"：实测 BWIKI 没有轮换货架，`商店一览` 里
> `#2002 远行商人` 只登记 1 件常驻商品，正文提到远行商人的条目只有 3 个。
> 清单必须能自己长大，否则新道具永远选不到。

### 新增：已购买标记

- 卡片右上角「○ 标记」，点一下变「✓ 已购」，商品自动移到下方独立的「已购买」区
- 已购卡片整体压暗、价格变灰，不再抢注意力；再点一次即可撤销
- 标记按**轮次**记录：换货后自动失效。下一轮同样的商品如果又上架，应该重新提醒，
  而不是继承上一轮的勾选

### 修复：24 点后仍显示昨日商品

**现象**：过了 00:00，界面还列着昨天 20 点那一轮的货架，没有任何提示说明它是旧的。

**根因**：数据源在打烊后并不会清空，页面仍挂着 20 点那一轮；而轮次计算在
00:00–08:00 返回 0，`filter_by_round()` 见到假值会**原样返回全部条目**，
于是昨日货架一路穿到界面上。上游 JSON 渠道更直接：缓存里的 `status` 还写着 `open`。

**修复**：营业时间是本地就能确定的事实，不需要相信接口。三层同时兜底：

1. `providers` 在非营业时段把 `items` 清空、`status` 强制为 `closed`（页面与 JSON 两条路径都改）
2. 主窗口渲染前再判断一次当前时间，非营业时段一律按"已打烊"展示
3. 悬浮窗同样不列商品——否则它会成为漏网之处

打烊占位文案也补了一句"打烊期间不显示上一轮的货架"，避免被误读成"正在补货"。

### 界面微调

- 「○ 标记 / ✓ 已购」按钮加大（字号 8→9、内边距加倍），并加了悬停反馈，
  不再是一行看起来不可点的小字
- 历史区域的展开控件从一行小字换成 104×30 的圆角按钮（「展开历史 / 收起历史」），
  整行标题也可以点
- 悬浮窗标题栏的 `⟳` / `◉` / `–` / `✕` 统一放大（标题栏 34→38px），点击区域约 30px
- **展开后的历史不再是纯文本**：复用主界面的商品卡片（图标、珍惜度色条、中文价格、
  内边距与圆角全部一致），一眼就能和"当前的货架"对上
